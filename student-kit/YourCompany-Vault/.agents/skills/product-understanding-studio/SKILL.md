# 產品／服務理解工作室

先理解賣甚麼、買家為何需要及有甚麼證據，再交接設計。產品與服務共用以下關卡，只讀適用細節。文件由 AI 整理，客戶用自然語言回答即可。

## 1. 確認任務

讀已有資料與對話，辨認 product、service 或 hybrid，不要求客戶選 mode。簡述已知內容，集中問仍會改變工作嘅缺口：受眾／市場、成果／平台、主打／CTA、必用品牌素材及參考。

新任務先取得這輪答覆再研究；已清楚確認的項目直接沿用，不為換 Skill 重問。資訊齊但尚未確認時，用一句摘要取得確認。原資料閱讀可先做，不能自行補定銷售策略。對話例子見 [classroom-dialogue.md](references/classroom-dialogue.md)。

## 2. 按類型研究，確認理解

讀 [public-product-research.md](references/public-product-research.md)，按 [product-baseline.md](references/product-baseline.md) 整理一份 `offer-notes.md`；已有等效筆記直接重用。

| 類型 | 核對重點 |
| --- | --- |
| 產品 | 款式／版本、外觀、材質／成分、規格、用法、適配及限制 |
| 服務 | 對象、包括／不包括、方法／流程、交付、參與條件、價格／方案及承諾 |
| 混合 | 同一筆記分開兩者事實，說明套裝關係；不重跑開場 |

每個重要特點連到來源、買家意義及可用文案；分清事實、客戶問題、推測與 TBC。研究深度由買家問題與本次用途決定，不湊網站、問題或賣點數量。

展示理解摘要、可用主打及重要缺口，問「呢個理解同主打啱唔啱？」並等待確認，才進入視覺製作或交接。修正只回到受影響部分；已有同範圍有效確認可沿用。

## 3. 按需要核對視覺

先看原素材能否支持預計畫面，再按 [usage-cases.md](references/usage-cases.md) 判斷是否需要理解預覽。沒有疑問可直接交接；不固定五張，也不以生成圖代替證據。

- 產品：檢查會被展示的外觀、細節及操作，讀 [product-form-lock.md](references/product-form-lock.md)；需外觀總覽才讀 [appearance-sheet.md](references/appearance-sheet.md)。
- 服務：核對會被展示的流程、交付物、人物身份及實際範圍；清楚的文字資料不必再生成流程圖。
- 混合：只核對本次畫面涉及的部分。

需要預覽時，說明問題、素材、張數及限制，可併入理解確認一輪批准。按 [visual-execution.md](references/visual-execution.md) 製作，讓客戶核對仍有疑問的部分。缺證據就補來源或改用受支持畫面；不能靠 AI 補未知背面、操作或成果。已批准的預覽未完成要記明，不能靜默略過。

## 4. 交接

按 [handoff.md](references/handoff.md) 保留已確認事實、主打、素材、缺口、預覽狀態及下一個成果。只要研究便到此交付；原任務包含設計時，實際讀取本地 `brand-image-studio/SKILL.md` 接手。

交接不要求固定圖片數、重複報告或先規劃詳情頁。原素材及來源持續作事實依據；生成圖只作示意。
