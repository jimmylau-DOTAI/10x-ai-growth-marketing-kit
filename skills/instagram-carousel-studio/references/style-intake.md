# Style Intake

## Route Order

1. Existing approved project-local Style Capsule.
2. Supplied reference images.
3. Four bundled Starter Styles.

Never ask for references when the user already selected a valid Style. Never invent a brand Style from one attractive image without marking it a candidate.

## Reference Roles

Classify every supplied file as one of:

- `style-reference`: layout, lighting, material, hierarchy, or composition.
- `identity-reference`: person, product, mascot, or distinctive object that must remain recognizable.
- `content-or-proof-reference`: screenshot, chart, quote, or evidence to appear in a card.
- `brand-asset`: official logo, font, palette, or lockup.
- `edit-target`: an existing output to revise.

One file can hold more than one role, but record the roles explicitly.

## Deconstruction

For each visually distinct cluster, record:

- layout and focal path
- type hierarchy
- palette and contrast
- material, texture, lighting, and depth
- subject grammar
- UI, proof, diagram, or icon grammar
- density and whitespace
- logo safe zone
- fixed, adjustable, content-dependent, and forbidden traits
- prompt block and negative block

Do not average four incompatible references into one vague Style. Make separate Capsules and let the user choose.

## Four-Option Comparison

- Use identical headline, subtitle, CTA, brand inputs, and aspect ratio.
- Change only design mechanisms.
- Make options materially different at a glance.
- Label them A–D outside the final card artwork, not as part of the post.
- A selection is `STYLE_SELECTED_FOR_PROJECT`, not universal proof that the Style works.

Raw user references stay in the consuming project. Do not copy them into the distributable Skill.
