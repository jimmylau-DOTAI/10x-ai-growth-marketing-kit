# Platform routing and Design ID

Use this reference when the current task already has a known platform/format, or the user asks to file or relocate a Style. Resolve that context before choosing a generic portable destination.

## Discover and file

1. Read the current Vault rules, exact format INDEX and DESIGN Style Router. Reuse any established named-Style directory and reference area.
2. Duplicate-check the Style. Follow an existing candidate-library route when present. When the user requests multiple candidate options and no library exists, create a format-local Style-Candidates/INDEX.md and one folder per style_id; link the format Router to this catalogue. Otherwise use the existing named-Style route. Existing Styles can be indexed by link without duplicating or moving their source packs. Do not invent empty Styles or a Design ID scheme.
3. New packs keep one STYLE.md and permitted reference images together; optional writing TONE only if requested. Legacy packs retain their existing five-file contract. Use the actual style_id/platform_scope and working relative image links; do not create duplicate DESIGN or REFERENCE for a version 2 pack.
4. Before changing files, state source, destination, changes and affected scope. A current-task request to save or move the identified Style supplies authorization for that action; do not ask for the same approval again. Analysis alone supplies no write authorization. Resolve real overwrite conflicts before proceeding.
5. The current authorized owner can perform the local filing. Update the format INDEX/Router and consuming Project paths. Keep one editable canonical pack; old paths may contain redirect notes for compatibility.
6. Read back the destination, links, scope, status and reference hashes. Record the outcome in the existing index or STYLE confirmation section, not a mandatory extra receipt. Report what was saved and what was checked; do not imply publication or cross-topic validation.

## When to use Visual-Styles

Use the portable Visual-Styles root when the user explicitly wants a general pack, or when the Vault lacks a corresponding format area. Do not select it merely because save_style_pack.py defaults to that path. The portable script is optional for format filing.

## Existing Design ID systems

Only when the destination already manages namespaces/Design IDs, use assets/templates/PLATFORM-ROUTE.md and scripts/validate_platform_route.py. This is an optional legacy managed-library receipt, not a required per-Style file. Inspect existing IDs and choose a free ID under that established namespace. New STYLE.md metadata must agree with the route; legacy DESIGN must also agree. Never invent an ID namespace or create DESIGN just to satisfy routing. An ordinary named Style uses the existing format index directly.

## Adaptation versus relocation

Library status, Project selection and format-wide default are separate. A saved candidate may be selected for one Project while remaining one of several library options. Only an explicit default-setting request changes the format default; saving or choosing an option does not. Keep the candidate catalogue concise and read only the selected pack.

Moving an existing Carousel Style into its Carousel folder changes its location and declared scope, not its visual rules. Reusing it across a new format requires reviewing reading order, canvas, density, safe areas and proof needs for that format. User-selected status records an actual user choice; limited testing remains an evidence note, not a repeated approval gate.
